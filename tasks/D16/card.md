# D16 — Compile a request into a rubric before any candidate exists

**Generator:** precommitment-contract recovery. **Stage × artifact:** eval/grading × code. **Modality:** experimental requests and executable predicates.

## Problem

An inherited evaluator writes acceptance rules after seeing a candidate, allowing candidate cues to shape the standard. Submit a bounded total rubric program derived only from the request, then freeze it before candidate generation. [Suite 9.12](/workspace/task_suites_claude.md:12733) studies reusable executable acceptance semantics, not candidate-conditioned validity prediction.

## Why known recipes plateau

A literal typed request compiler, rule induction and property-based testing may completely solve the supported language. The source audit already identifies that risk. Sparse examples do not create research depth when the request unambiguously describes an enumerable conditional program; ambiguity instead invalidates the grading target.

## Deterministic grader

Freeze the rubric hash and execute it on fresh candidates with independently constructed extensional truth. U is balanced agreement over satisfied, violated and boundary obligations, using fixed denominators. Timeouts and non-total programs fail their affected cases. Equivalent correct programs are accepted regardless of syntax; apply F_D16 without an LLM grading the rubric's prose.

## Hidden-score design

New request compositions and independently implemented candidate producers form the private bank. Dev exposes the same request semantics and a protected composition proxy. Neither compiler nor rubric sees later candidate identity at synthesis time, and sample files cannot reveal future answer labels.
